# 🥗 다이어터를 위한 냉장고를 부탁해

**냉장고 사진을 올리면, 내가 고른 다이어트 방식에 맞는 요리를 영양 정보와 함께 알려주는 앱**

사진 속 재료를 이미지 인식으로 찾아내고, 선택한 **다이어트 모드**(혈당관리·칼로리관리·근육증량·
체지방감소·카니보어·키토·지중해식)의 기준으로 요리 3가지를 추천합니다.
같은 재료라도 모드가 바뀌면 추천도, 결과 카드에서 강조하는 숫자도 달라집니다.

## 다이어트 모드 7종

| 모드 | 대상 | 탄 : 단 : 지 | 크게 보여주는 숫자 |
| --- | --- | --- | --- |
| 혈당관리 | 식후 졸림·폭식이 잦은 사람 | 35 : 30 : 35 | 혈당 반응 |
| 칼로리관리 | 감량 입문자 | 40 : 30 : 30 | 열량 |
| 근육증량 | 웨이트 병행, 체중 정체 | 45 : 30 : 25 | 단백질 g |
| 체지방감소 | 체성분을 바꾸고 싶은 사람 | 30 : 40 : 30 | 단백질 g |
| 카니보어 | 제거식이 실험 중 | 0 : 30 : 70 | 지방 : 단백질 |
| 저탄고지·키토 | 식욕 억제가 필요한 사람 | 7 : 23 : 70 | 순탄수 g |
| 지중해식 *(기본값)* | 특정 목표 없이 건강하게 | 45 : 20 : 35 | 열량 |

모드는 [lib/modes.ts](lib/modes.ts)에 데이터로만 정의되어 있습니다. 새 모드를 넣는 일은
배열에 객체 하나를 더하는 일이고, 프롬프트와 화면은 그 객체를 읽어 동작합니다.

## 설정은 다섯 축으로 나뉜다

목표와 제약을 한 필드에 섞으면 "비건 × 근육증량" 같은 정상적인 조합을 표현할 수 없습니다.
그래서 축을 나눴습니다.

| 축 | 필드 | 성격 |
| --- | --- | --- |
| 목표 | `mode` | 7종 중 하나 |
| 제한 | `restrictions[]` | 베지테리언·비건·할랄·유당·글루텐 (복수 선택) |
| 안전 | `allergies[]` | 최우선. 코드로 강제한다 |
| 스케줄 | `fastingWindow` | 없음 / 16:8 / 18:6 / 하루 한 끼 |
| 취향 | `spice` `maxMinutes` `cuisines` `dislikes` | 목표를 지킨 뒤의 동점 처리용 |

모드와 모순되는 제한(카니보어 × 비건 등)은 화면에서 비활성화되고, 서버 저장 시에도 떨어집니다.

## 목표 열량 계산

성별·나이·키·몸무게·활동량을 넣으면 Mifflin-St Jeor로 유지 열량을 구하고, 모드의 계수를 곱해
하루 목표를 냅니다. 단백질은 열량 비율이 아니라 **체중 kg당 목표**로 먼저 확정합니다 —
비율에서 역산하면 감량 중에 단백질이 같이 깎이기 때문입니다.

신체 정보를 넣지 않으면 목표 열량 없이 "일반적인 1인분" 기준으로 추천합니다.
억지로 기본값을 넣어 근거 없는 숫자를 보여주지 않습니다.
하루 목표는 **1,200kcal 아래로 내려가지 않습니다**.

## 하드룰은 코드가 강제한다

모드의 하드룰과 알러지는 프롬프트로도 전달하지만, 그것만 믿지 않습니다.
응답을 받은 뒤 [lib/rules.ts](lib/rules.ts)에서 다시 검사해 어긴 레시피를 버립니다.

- 카니보어인데 식물성 재료가 들어갔으면 → 버림
- 키토인데 1인분 순탄수가 20g을 넘으면 → 버림
- 알러지로 등록한 재료가 **조리법 문장에라도** 나오면 → 버림
- 열량·단백질이 모드 목표를 크게 벗어나면 → 버림

버려진 레시피가 있고 남은 게 2개 미만이면, 무엇이 왜 버려졌는지 알려주고 **한 번만** 다시
요청합니다. 그래도 안 되면 사용자에게 모드나 재료를 바꾸라고 말합니다.
화면에도 "걸러낸 요리"를 이유와 함께 보여줍니다.

> 키워드 매칭은 완벽하지 않습니다. 조리법 문장까지 훑기 때문에 짧은 낱말은 넣을 수 없습니다
> ("무"는 "너무"에, "간"은 "중간에"와 "간장"에 걸립니다). 놓치는 쪽보다 과하게 거르는 쪽으로
> 목록을 짰습니다.

## 결과 카드

- 선택한 모드 기준 **적합도 0~100**과 그 근거 한 문장
- 1인분 기준 **열량 · 탄수 · 단백질 · 지방 · 식이섬유 · 나트륨**
- 목표 열량 대비 초과/여유를 숫자로
- **대체 재료 제안** — "설탕 → 알룰로스 · −48kcal" 처럼 변화량과 함께
- **먹는 순서** — 혈당관리 모드에서 채소 → 단백질 → 탄수
- 영양 수치가 AI 추정값이라는 고지

## 기술 스택

- **Next.js 14** (App Router) — 프론트엔드 + API를 한 프로젝트에서
- **TypeScript**
- **Google Gemini API** (`@google/genai`) — Vision 이미지 인식 + 구조화 출력(JSON Schema 강제)
- **PostgreSQL** (Supabase) — 설정과 추천 기록 영구 저장
- **Vercel** 배포

## 동작 흐름

```
사진 촬영 → 브라우저에서 1536px 리사이즈 → /api/analyze
                                              ↓ Gemini Vision
                                         재료 목록(JSON)
                                              ↓ 사용자가 확인·수정
  DB의 프로필 ─→ 모드 스펙 주입 ─→ /api/recommend
                                              ↓ Gemini (구조화 출력)
                                     요리 3개 + 영양 + 적합도
                                              ↓ lib/rules.ts 검증  ← 신뢰 경계
                                     통과한 것만 DB 저장 후 응답
```

## API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `GET` | `/api/profile?user=<key>` | 저장된 설정 조회 (없으면 기본값) |
| `PUT` | `/api/profile?user=<key>` | 설정 저장. 모드와 모순되는 제한은 여기서 떨어짐 |
| `POST` | `/api/analyze` | 이미지(base64) → 재료 목록 |
| `POST` | `/api/recommend?user=<key>` | 재료 + 프로필 → 검증을 통과한 요리, 결과를 DB에 저장 |
| `GET` | `/api/history?user=<key>` | 최근 추천 기록 10건 (당시 모드 포함) |

로그인이 없으므로 브라우저가 `localStorage`에 만든 임의 키(`user`)로 사용자를 구분합니다.
서버는 이 키를 `^[A-Za-z0-9_-]{8,64}$` 로 검증합니다.

테이블 `dinner_profiles` / `dinner_sessions` 는 첫 요청 시 자동 생성되고, 다이어터 버전에서
늘어난 컬럼은 `ADD COLUMN IF NOT EXISTS` 로 얹힙니다. 구버전의 단일 `diet` 필드는
목표(`mode`)와 제한(`restrictions`) 두 축으로 자동 이관됩니다.

## 로컬 실행

```bash
npm install
cp .env.example .env.local   # GOOGLE_API_KEY, DATABASE_URL 입력
npm run dev
```

http://localhost:3000 접속.

### API 키 발급

1. https://aistudio.google.com/apikey 접속 → 로그인
2. **Create API key** 로 키 생성
3. `.env.local` 의 `GOOGLE_API_KEY` 에 입력
4. 배포 환경에서는 Vercel 프로젝트 환경 변수에 같은 이름으로 등록

키가 없으면 사진 분석과 추천 요청이 `503` 과 함께 안내 메시지를 반환합니다.

## 비용에 대한 참고

이미지는 업로드 전에 긴 변 1536px로 줄여서 보냅니다. 재료 인식은 `thinkingLevel: LOW`,
메뉴 추천은 `HIGH` 로 호출합니다. 영양·적합도 필드가 늘어나면서 추천 응답의
`maxOutputTokens` 는 16,000 → 24,000 으로 올렸습니다.

검증에 걸려 재요청이 발생하면 추천 호출이 2회가 됩니다. 재요청은 한 번으로 제한됩니다.

## 안전에 관한 고지

이 앱이 보여주는 영양 수치는 AI가 재료에서 추정한 값이며 **의료·영양 조언이 아닙니다.**
혈당관리 모드는 질환 관리를 대신하지 않고, 카니보어·키토 모드에는 결핍 위험 경고를 함께
표시합니다. 하루 목표 열량에는 하한(1,200kcal)을 두었습니다.
